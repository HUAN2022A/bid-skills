# bid-recall：历史标书召回

大纲确认后，逐章从**历史标书库**（`标书/历史标书/*.docx`，人为完成的真实投标终稿）召回相似章节和图片，供起草时**整章打底改写**。**这是召回阶段，不是改写阶段**——产出的 recall-pack.yaml 是"哪些历史内容可用、怎么用、旧值怎么换新值"的施工单，改写发生在 bid-draft（改写引擎，消费本 skill 的产物）。

## 设计要点

- **目录即库**：历史标书库就是 `标书/历史标书/` 文件夹，无独立数据库。索引（`标书/_recall-index.yaml`）+ 章节全文（`标书/_recall-sections/`）+ 图片库（`标书/_recall-figures/`）均为可再生缓存，删掉重跑 build_index.py 即重建。
- **两段式召回**：脚本粗筛只求不漏（确定性计分，可复现）；语义裁决交给 LLM 精筛（判断"能不能搬、怎么搬"是技术判断，不是相似度计算）。
- **图片召回 = 纯图注匹配**：图注从 docx 图片下一段提取（"图：xxx"格式），按图注规则判图型，跨文档按内容哈希去重。无 OCR、无向量模型、零外部服务。
- **召回源红线**：只收人为完成、真实投标的历史稿；AI 生成的项目工作区（`标书/生成的标书/`）和外部获得的中标范文**不入库**（范文只学写法不抄内容）。

## 输入与前置检查（不满足则停止并提示）

- `{项目}/bid-outline.yaml` 存在且 `status: confirmed`——大纲未确认不做召回（章节树未定，query 无从构造）。
- `标书/历史标书/` 存在且含 docx——没有历史标书就提示本阶段跳过，直接 bid-draft。

## 流程

### 1. 构建索引（历史标书有更新时）

```
python <本skill目录>/build_index.py
```

按 Heading 样式切章节（最细 H3，H4/H5 归并）、**每章全文导出为 md**（正文+表格还原+图片引用，落 `_recall-sections/<项目slug>/`）、抽取全部内嵌图片落盘（`_recall-figures/<项目slug>/`）、提取图注、跨文档哈希去重、章节关键词自动提取（数字+单位/品牌型号/引号词+高频领域术语）。输出 `标书/_recall-index.yaml`。历史标书没变可不重跑。

### 2. 粗筛

```
python <本skill目录>/recall_search.py -d {项目目录}
```

每叶章节构造 query（标题 + 挂的评分点/技术需求展开的关键词 + notes），对索引计分：

- 章节：标题 bigram 相似 ×0.4 + 关键词命中 ×0.35 + 评分点/需求关键词命中 ×0.25
- 图片：图注命中 ×0.6 + 所属章节得分传导 ×0.4
- 同标题跨文档、同文档嵌套路径自动去重（留分高者）

输出 `{项目}/recall-candidates.yaml`：每章 top-8 章节 + top-12 图。

### 3. LLM 精筛（本 skill 的核心判断）

读 recall-candidates.yaml，逐章对每个候选裁决。**判断依据是技术相关性，不是分数**——分数只排序，裁决看 heading/path/first_text 与新章的实际关系。

**章节 mode 裁决标准：**

| mode | 判定条件 |
|---|---|
| 打底改写 | 与新章同技术域（如同为摘钩方案/视觉识别/联锁设计），历史节内容可整体搬结构：保留技术骨架、替换项目特定信息后重写。参考线：score≥0.35 且 words≥300，但结构章（工程量清单/偏离表）即使高分也降级 |
| 部分引用 | 不同域但含可搬的段落/表格/参数表述（如历史"整机性能验收大纲"之于新章"性能保证"），只引用局部 |
| 不用 | 结构性章节或主题无关 |

**同项目多版本**：candidates 已按标题去重；需要看全文时优先取文件名更新（版本后缀更近）的 doc。

**图片 action 裁决标准：**

| action | 判定条件 |
|---|---|
| 直接复用 | fig_type 与新章配图需求匹配，且 shared_by≥2（通用图，多项目共用无串味风险），如通用流程图/示意图 |
| 照片需核实 | 现场照片/设备图——真实照片才可配，但必须核实设备型号与本项目一致（图不能改，张冠李戴反减分） |
| 重生成参照 | 甘特/进度/部署平面类含项目特定参数的图——历史图只作"这里曾配过什么图"的参照；**图片内容以召回为主，不再生成示意图**，此类图默认不配图（或人工另行绘制） |

**替换表草稿**：从索引 `docs[].first_text` 与新项目 tender-analysis 元数据，生成项目级"旧值→新值"映射（项目名称、招标人、地点、工期、数量、机型）。LLM 补充从候选 first_text 里发现的量纲差异。

### 4. 产出 recall-pack.yaml 并确认（唯一人工确认点）

```yaml
project: 新项目名
status: draft        # draft | confirmed（用户确认后改 confirmed）
generated_at: 日期
replacements:        # 项目级替换表（bid-draft 改写时逐项替换，串味扫描的词表来源）
  - {field: 项目名称, old: 甘肃电投常乐…, new: 淮北国安…}
  - {field: 工期, old: …, new: 90日历天}
chapters:
  - id: "1.4"
    title: 摘钩机器人技术方案
    text_hits:
      - {doc: xxx.docx, path: "实施方案 / 摘钩机器人部署", md: _recall-sections/xxx/013-xxx.md,
         mode: 打底改写, reason: 同为摘钩机器人方案，结构可搬, words: 2507}
    figure_hits:
      - {hash: ab12…, extracted: 标书/_recall-figures/…/010-image20.png,
         caption: 图：摘钩机器人部署平面图, fig_type: 部署图, shared_by: 1文档,
         action: 直接复用}
```

**一次性向用户展示**：每章命中与 mode、图片建议、替换表。用户删改勾选后改 `status: confirmed`。确认后不再追问（提一次即止）。

### 5. 衔接

- recall-pack confirmed 后进入 `/bid-draft`（改写引擎）：打底章按 `md` 路径读全文微调修改、按 `replacements` 替换旧值、按 `figure_hits` 复制落地图片——详见 bid-draft/SKILL.md 的"改写模式"。
- 索引与候选清单（recall-candidates.yaml）是中间产物，不随标书交付。

## 边界

- 只召回不改写；不修改历史标书库和索引之外的任何文件（_recall-figures/ 是抽取副本，不动原始 docx）。
- 历史标书内容含旧项目敏感信息（业主名、报价旁证等），recall-pack 只在本项目工作区内流转；引用到新标书的内容由 bid-check 串味扫描把关（残留旧项目专有信息即报警）。
- 图注缺失的图（约半数）只能靠所属章节传导召回，caption 为空不代表不可用——精筛时看 in_path 判断。
- 换电脑/换库：整个 `标书/` 文件夹拷走即迁移；索引可重建，不是状态。
