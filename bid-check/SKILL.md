# bid-check：符合性自查

标书提交前的机器自查。核心逻辑：**评分点对照表是全流程的中枢契约**——bid-parse 提取评分点、bid-outline 挂到章节、bid-draft 逐章响应，bid-check 则回头核对"每个评分点/技术需求到底有没有被响应到位"。只检查、不修改，发现的问题列清单。

## 输入

当前目录（或用户指定）下的：`tender-analysis.yaml`、`bid-outline.yaml`、`chapters/*.md`。

## 三类检查

### 1. 评分点覆盖率矩阵

对每个 `category: 技术` 的评分项：
- 它在 outline 里挂了哪些章节？
- 那些章节的 `.md` 是否存在、是否有实质内容？
- 章节头部的 `covers` 注释是否声明覆盖了该评分点？

输出矩阵：评分项 → 章节 → 覆盖状态（已响应/章节缺失/未声明）。

### 2. 技术需求逐条响应核对

对每条 `tech_requirements`（尤其硬指标）：
- 在 chapters 里 grep 关键数字/关键词（如"97%""10秒""3000N""臂展"），判断是否被响应；
- 硬指标是否给出"招标要求|我方响应"的明确响应。

### 3. 废标风险 + 格式核对 + 缺口

- **废标风险**：对照 `disqualification` 清单，标注技术卷相关的风险点（如技术参数未实质响应、技术偏离表缺失、关键技术响应表缺失）；
- **格式核对**：章节是否齐全（对照 outline 叶章节）、章节编号是否与 outline 一致、技术卷是否混入报价信息（grep 价格/报价/万元等敏感词，命中则提示）；
- **[待补]缺口**：汇总所有章节的 `[待补]`，列出哪些内容缺素材/缺人工补充。

## 流程

1. 读三个输入文件；
2. 跑 `check_bid.py` 做机器可判定的检查（覆盖矩阵、关键词命中、待补扫描、章节齐全性）；
3. 模型补充**需要判断的检查**（响应是否"实质"、是否"优于招标要求"、措辞是否回扣评分标准）——这部分机器判不了，逐章读给结论；
4. 写 `{项目}/check-report.md`，含：评分点覆盖矩阵、技术需求响应表、废标风险清单、格式核对结果、[待补]缺口清单、**人工处理清单**（商务/价格/资质类，提醒人工完成）；
5. 向用户汇报：通过项、风险项、缺口项，以及建议回 bid-draft 补写的章节。

## 输出 check-report.md 结构

```markdown
# 符合性自查报告
## 一、评分点覆盖率矩阵
## 二、技术需求逐条响应
## 三、废标风险清单
## 四、格式核对
## 五、[待补]缺口清单
## 六、人工处理清单（商务/价格/资质）
## 七、结论与建议
```

## 边界

- 只检查不修改——发现问题列清单，由用户决定回 bid-draft 补写还是人工处理。
- 商务/价格/资质类内容不在技术卷范围，但要在"人工处理清单"里提醒，防止静默遗忘。
- 机器能判定的（覆盖、关键词、待补、章节齐全）用脚本；需要判断的（响应质量、是否优于）用模型逐章读。
