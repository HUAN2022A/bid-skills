# bid-draft：逐章改写引擎

按确认的 `bid-outline.yaml` 产出每章 markdown。**起草的本质是"按新招标要求微调修改召回的历史真实稿"，不是从零写作**——历史真实稿（人写的、真投过的）是正文主体和技术深度的来源，AI 的角色是编辑/适配器。只有历史库覆盖不到的章节才走生成兜底。

## 输入

当前目录（或用户指定目录）下：

- `bid-outline.yaml`（`status: confirmed`，否则拒绝开写）
- `recall-pack.yaml`（bid-recall 产物，`status: confirmed`）——**主输入**。不存在时提示"跳过了召回，全部章节将从零生成"，并建议先跑 `/bid-recall`
- `tender-analysis.yaml`
- 素材卡片库（`~/Documents/company-knowledge/`）

## 硬约束（违反即返工）

1. **公司硬事实双源制**：数字类资格事实（金额/职称/数量/日期）以素材卡片为准，卡片没有的先回填卡片再写；叙述性事实（技术方案、项目经历、实测叙述）可引用召回的历史稿——历史稿本身是公司真实材料。两边都没有的写 `[待补：需要XX]`，**绝不编造**。
2. **逐条响应**：章节挂的 `scoring` 评分项和 `tech_reqs` 技术需求，正文里必须有明确响应段落；技术参数逐条给出响应值且**响应值 ≥ 招标要求**。
3. **不照抄招标文件**：可引用标准条款，技术方案必须改写重组。
4. **技术卷禁含报价**。
5. **联网边界**：可联网查外部技术事实，查询内容不得携带公司敏感信息。
6. **章节编号稳定**：正文标题编号与 outline 的 `id` 一致。
7. **串味零容忍**：改写章残留旧项目任何专有信息（业主名、项目名、地名、工期、数量、机型）即为缺陷，写完自查一遍再落盘（bid-check 会再扫一遍）。

## 改写模式（有召回打底的章节）——主路径

### 上下文组装（每章）

1. recall-pack 本章条目：打底章节的 `md` 全文路径（`标书/_recall-sections/…`）、`mode`、`figure_hits`
2. recall-pack 的 `replacements` 替换表：项目名称、招标人/业主、地点、工期、数量、机型的"旧值→新值"
3. tender-analysis 抽出：本章 `scoring` 的 `criteria_original`、`tech_reqs` 的 `requirement_original`
4. 打底 md 全文（整文件读入，图片引用保持原路径）

### 改写指令（核心）

- **保留**：技术骨架（技术路线、算法名称、机械结构、作业流程）、全部图片及其对应正文、实测数据与案例叙述、参数表格——这些是人工稿的价值所在，不要"润色"掉具体性。
- **替换**：按替换表换项目特定信息，旧业主/旧项目名/旧地名/旧工期一处不漏；正文里出现的替换表没覆盖的旧值（如旧项目专属参数），改成新标对应值或删除。
- **差异核对**（改写的核心质量所在）：逐条比对新标 `tech_reqs` 与打底稿的响应——
  - 历史稿未响应的需求 → 补写响应段落；
  - 历史稿响应值低于新标要求 → 改为满足（**参数必须有依据**：素材卡片或历史稿里有公司能力支撑才写新值，否则标 `[待补：需确认能力]`）；
  - 历史稿响应了新标没有的旧需求 → 删除或弱化为通用描述。
- **评分点对齐**：新标 `scoring` 每项的措辞要有回扣段落；历史稿没有对应内容的按评分标准原文补写。
- **图片落地**（必须完成的机械动作）：
  1. 打底 md 里的 `![…](../../_recall-figures/…/xxx.png)` → 把图**复制**进 `{项目}/figures/`（命名 `{新章id去点}-{原名}`，如 `1-4-010-image20.png`；同名冲突加来源项目短名前缀），正文引用改为 `(figures/新名.png)`；
  2. 图注重排为 `图 {一级章号}-{章内序号} {图注}`，序号从 1 起按章内出现顺序（跨文件连续，与 bid-check 规则一致）；
  3. recall-pack `figure_hits` 中 `action: 直接复用` 的图（通用图），即使打底正文没引用，也可按配图原则择优插入合适小节；
  4. `action: 照片需核实` 的现场照片：可以插入，但**当次汇报必须列出"照片待核实清单"**（图名 + 疑似设备型号），不得默默使用；
  5. 无图可配时宁可不配图，也不生成示意图。
- **禁止**：整段照抄不动（至少项目特定信息全部替换）；删除图片对应的正文叙述；把人工稿的具体参数"泛化"成空话（如把"PicoDet+SVTR，识别率99.2%"改成"采用先进深度学习技术"）。

### 写完落盘

- 写 `{项目}/chapters/{id}-{slug}.md`，章标题 `# {id} {title}`
- 篇幅向 `target_words` 靠（打底稿字数与新标要求差太多时，以覆盖评分点为准，不为凑字注水）
- 文件头部 covers 注释、每章简短汇报（响应了哪些评分点/需求、复制了哪些图、留了几个 `[待补]`、照片待核实清单）

## 生成模式（无召回打底的章节）——兜底

走原有生成流程：卡片关键词匹配素材 + 招标文件相关段落 + 联网查证 → 逐条响应撰写。

- 公司事实仍只准引用素材库/召回库；
- 配图顺序：本章在 recall-pack `figure_hits` 里若有可用图 → 用之（同图片落地规则）；无召回图则不配图——**图片内容以召回为主，不再生成示意图**。

## 流程

### 1. 前置检查 + 断点扫描

outline `status: confirmed`；读 recall-pack（无则提示后继续，全走生成模式）。扫描 `chapters/` 已有 `.md` 对照叶章节清单得待写章节。已有内容的章节跳过（除非用户点名重写）。

### 2. 逐章产出

按 outline 顺序：有 recall-pack 打底条目 → 改写模式；无 → 生成模式。每章独立文件，随时可中断续作。用户可点名只写某章：`/bid-draft 2.5`。

### 3. 全部写完后

总览汇报：章节数、总字数、改写章/生成章各多少、复制落地的图片清单、`[待补]` 汇总、**照片待核实总清单**、提示下一步 `/bid-check`（串味扫描会在那里再把关一次）。

## 写作质量要求

- 技术方案**具体**：算法名称、网络结构、量化参数——人工稿里已有的具体性是资产，保留而非淡化。
- 每个评分点响应段落**回扣评分标准原文措辞**。
- 硬指标响应用**表格**（招标要求 | 我方响应 | 偏离情况）。
- 改写章的图表来自历史真实稿，图文天然自洽——改动正文时不得破坏这种对应（图对应的段落不能删）。

## 配图（图文并茂）

**图片内容以召回为主**：配图 = recall-pack `figure_hits` 中 `直接复用` 的历史真实图（流程/架构/部署等）+ `照片需核实` 的现场照片（核实设备一致性后使用）。**不再生成示意图**（make_figures.py 已删除）；无召回图时宁可不配图。图注编号规则不变；图里的技术内容必须与正文一致。

## 边界

- 不改大纲结构（发现结构问题提示回 bid-outline）。
- 不写商务/价格卷内容。
- 素材缺口标 `[待补]` 后继续写其余部分。
- 不修改 `标书/历史标书/`、`_recall-figures/`、`_recall-sections/` 的任何文件（只读+复制）。
