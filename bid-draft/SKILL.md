# bid-draft：逐章起草

按确认的 `bid-outline.yaml` 把每个叶章节写成 markdown。**这是体力活阶段，不是设计阶段**——结构已定，任务是逐章填肉、逐条响应评分点和技术需求。

## 输入

当前目录（或用户指定目录）下的 `bid-outline.yaml` + `tender-analysis.yaml`。

**前置检查（不满足则停止并提示）：**
- `bid-outline.yaml` 的 `status` 必须是 `confirmed`。是 `draft` 就提示用户先确认大纲（bid-outline 阶段），**拒绝开写**。
- 找不到 `bid-outline.yaml` 就提示先跑 `/bid-outline`。

## 硬约束（违反即返工）

1. **公司事实只准引用素材库**（双层，分工见「上下文组装」第 3 步）：资格硬事实（金额/职称/数量/日期）以卡片为准，卡片没有的先回填卡片再写；叙述性素材可引用召回后端原文，数字原样照抄。两边都没有的，写 `[待补：需要XX]`，**绝不编造**。
2. **逐条响应**：章节挂的 `scoring` 评分项和 `tech_reqs` 技术需求，正文里必须有明确响应段落。技术参数（成功率、臂展、负载等硬指标）逐条给出响应值，且**响应值 ≥ 招标要求**（"优于招标要求"才能进高档位）。
3. **不照抄招标文件**：可引用标准条款，但技术方案必须改写重组（tender-analysis F6 类要求）。
4. **技术卷禁含报价**（F4 类要求）。
5. **联网边界**：可联网查外部技术事实（行业规范、等保、信创目录、产品参数、技术标准），查询内容**不得携带公司敏感信息**；公司事实仍只来自素材库。
6. **章节编号稳定**：正文标题编号与 outline 的 `id` 一致，关键技术响应表要引用。

## 上下文组装（每章起草前）

为控制上下文，每章只组装该章需要的材料，不全量加载：

1. 该章在 outline 中的节点：`title` / `scoring` / `tech_reqs` / `target_words` / `notes` / `materials`
2. 从 tender-analysis.yaml 抽出：本章 `scoring` 对应评分项的 `criteria_original`（评分标准原文）、`tech_reqs` 对应技术需求的 `requirement_original`（需求原文）
3. 从素材库抽出：本章 `materials` 关键词匹配到的素材卡片内容（先 index.yaml 结构化过滤——资格硬指标必须走这层）。卡片覆盖不足、且运行环境提供召回后端（RAGFlow 等，见所在平台 AGENTS.md `## Tools`）时，再用评分点/章节关键词做一次语义召回补充原文段落（带来源文档名；从召回里发现的新硬事实先回填卡片再引用，规则见 company-knowledge 的「召回后端联动」）。无召回后端则纯卡片模式
4. 招标文件全文里与本章相关的段落（按需 grep，不全量读）

## 技术深度增强（新增）

为提升技术方案深度，每章起草前增加**技术卡片提取**和**参数优化**两个前置步骤：

### 1. 技术卡片提取

从 RAGFlow 检索结果中提取结构化技术卡片，确保技术描述具体到算法名称、结构组成、性能指标。

**领域自适应**：
- **不预定义固定模板**，由 LLM 根据章节内容自动识别技术领域
- LLM 根据领域特点，动态生成适配的技术卡片字段

**提取规则**：
1. **识别技术领域**：根据章节标题、技术需求、检索结果，自动判断属于哪个技术领域（如机器视觉、机器人控制、机械结构、网络架构等）
2. **生成领域字段**：根据领域特点，动态生成适配的字段（如机器视觉领域生成 detection/recognition/backbone，机器人控制领域生成 planning/interpolation/control）
3. **提取关键信息**：
   - **方法名称**：识别具体的技术方法（如 DB、SVTR、五次多项式、S 曲线）
   - **结构组成**：识别技术组成（如 ResNet-50、FPN、关节空间、笛卡尔空间）
   - **性能指标**：识别量化指标（如精度、速度、负载、臂展）
4. **标注来源**：每个字段必须标注来源（文档名+段落号）和置信度
5. **置信度规则**：多个文档提到相同内容，置信度提升；无明确来源，置信度降低

**领域示例**（供 LLM 参考，非固定模板）：
- **机器视觉**：detection/recognition/backbone/accuracy/speed
- **机器人控制**：planning/interpolation/control/accuracy/speed
- **机械结构**：structure/material/mechanics/load/stability
- **网络架构**：topology/protocol/security/bandwidth/latency

**输出格式（LLM 自适应）**：
```yaml
tech_card:
  tech_name: "技术名称"
  domain: "LLM 自动识别的领域"
  
  # LLM 根据领域动态生成的字段（参考上述示例）
  # 示例 1：机器视觉领域
  # detection: "DB"
  # recognition: "SVTR"
  # backbone: "ResNet-50 + FPN"
  
  # 示例 2：机器人控制领域
  # planning: "五次多项式规划"
  # interpolation: "直线/圆弧插补"
  # control: "七段 S 曲线速度规划"
  
  # 示例 3：机械结构领域
  # structure: "五类轮组复合结构"
  # material: "高强度合金钢"
  # mechanics: "主动轮/从动轮/导向轮/夹紧轮/防侧倾轮"
  
  performance:
    # LLM 根据领域动态生成的性能指标
    # 示例 1：机器视觉领域
    # accuracy: "99.2%"
    # speed: "200ms/帧"
    
    # 示例 2：机器人控制领域
    # accuracy: "±0.1mm"
    # speed: "2m/s"
    
    # 示例 3：机械结构领域
    # load: "120kg"
    # stability: "抗侧倾能力"
  
  source_trace:
    - field: "字段名"
      source: "文档名#段落号"
      confidence: 0.95
```

### 2. 参数优化

根据招标要求和公司能力，自动生成对比表述，从"满足招标"升级为"超越招标"。

**参数类型识别**：
- **数值型参数**：计算冗余度（如精度 99.2% vs 95%）
- **枚举型参数**：对比等级（如 IP65 vs IP54）
- **文本型参数**：对比描述（如"支持雨雾天气" vs "仅晴天"）

**优化规则**：
- **数值型参数**：
  - 计算冗余度：redundancy = (capability - requirement) / requirement
  - 根据冗余度选择策略：
    - redundancy > 20%：强调"显著优于招标要求 X%"
    - 5% < redundancy < 20%：表述为"满足并优于招标要求"
    - redundancy < 5%：表述为"完全满足招标要求，具备成熟应用经验"
- **枚举型参数**：
  - 如果等级更高：表述为"采用更高等级 XX，优于招标要求"
  - 如果等级相同：表述为"完全满足招标要求"
- **文本型参数**：
  - 如果功能更强：表述为"支持 XX，优于招标要求"
  - 如果功能相同：表述为"完全满足招标要求"

**输出格式**：
```yaml
optimized_statement:
  param_type: "数值型"  # 或 "枚举型" / "文本型"
  strategy: "强调冗余度"  # 或 "强调成熟度" / "强调等级" / "强调功能"
  statement: "99.2%，显著优于招标要求 4.2%"
  redundancy: 4.2%  # 仅数值型参数
```

### 3. 来源追溯

为每个技术参数标注来源，提高可信度，便于人工审核。

**追溯规则**：
- 每个技术参数必须标注来源（文档名+段落号）
- 使用 HTML 注释格式：`<!-- 来源：{field} 来自 {source}，置信度 {confidence} -->`
- 在 bid-check 阶段验证来源一致性

## 流程

### 1. 前置检查 + 断点扫描

读 outline 确认 `status: confirmed`。扫描 `{项目}/chapters/` 已有哪些 `.md`，对照 outline 的叶章节列表，得出**待写章节清单**。已有内容的章节跳过（除非用户点名重写）。

### 2. 逐章起草

按 outline 顺序对待写章节：

1. 组装上下文（见上）
2. **技术卡片提取**：从 RAGFlow 检索结果中提取结构化技术卡片（见「技术深度增强」）
3. **参数优化**：根据招标要求和公司能力，生成对比表述（见「技术深度增强」）
4. 写 `{项目}/chapters/{id}-{slug}.md`，markdown，章标题用 `# {id} {title}`，子节 `##`/`###`
5. 篇幅向 `target_words` 靠（中文按字符计）
6. **来源追溯**：为每个技术参数标注来源（见「技术深度增强」）
7. 写完在文件头部用 HTML 注释记录覆盖情况：
   ```
   <!-- covers: scoring=[S6] tech_reqs=[T1,T4,T5] materials=[案例卡-摘钩] pending=2 -->
   ```
8. 每写完一章，简短汇报：章节、字数、响应了哪些评分点/技术需求、留了几个 `[待补]`

### 3. 批量与中断

- 默认一次会话连续起草，但**每章是独立文件**，随时可中断——下次跑 `/bid-draft` 自动从断点续作。
- 用户可点名只写某章：`/bid-draft 2.5` 只起草 2.5 节。

### 4. 全部写完后

输出总览：章节数、总字数、`[待补]` 清单汇总（哪些章缺什么素材）、提示下一步 `/bid-check`。

## 写作质量要求

- 技术方案要**具体**：写清技术路线、选型、参数、算法、流程，不写"采用先进技术"这类空话。
- **算法具体化**：必须明确写出算法名称（如 DB、SVTR、YOLO），禁止只写"深度学习"。
- **结构拆解**：必须描述网络结构（如 ResNet-50、FPN）。
- **参数量化**：必须写出精度、速度、数据量。
- **冗余设计**：根据冗余度动态调整表述策略（见「技术深度增强」）。
- **来源追溯**：每个技术参数必须标注来源（见「技术深度增强」）。
- 每个评分点响应段落**回扣评分标准原文的措辞**（评分专家按评分标准找对应内容）。
- 硬指标响应用**表格**（招标要求 | 我方响应 | 偏离情况），一目了然。
- 子章节设计服务于该章评分点（outline 的 notes 已给写作要点）。

## 配图（图文并茂）

技术标书是图文并茂的。每章起草时判断是否配图，图存 `{项目}/figures/`，md 里用 `![图 X-X 名称](figures/xxx.png)` 引用（bid-export 导出时嵌入 docx）。

**三类图的来源与规则：**

1. **架构/流程/部署/甘特/数据图** —— 用 `<本skill目录>/make_figures.py` 生成（matplotlib，中文、风格统一、可批量）。已内置图型（`--only` 可单画）：`architecture` 架构图、`deployment` 部署图、`gantt` 甘特图、`flowchart` 作业流程图（判断菱形+分支回路）、`interlock` 安全联锁逻辑图（AND 条件门+危险停机支路）、`topology` 网络拓扑图（分层+DCS 硬线）。新图型往 `FIGS` 注册表加函数即可（`box/arrow/diamond/zone` 绘图原语已备好）。适合：系统架构图、网络架构图、部署示意图、作业流程图、感知-决策-执行-校验闭环图、进度甘特图、数据对比图。
2. **现场/设备照片** —— 从素材库历史标书抽取（company-knowledge 的抽图功能），配进案例（2.11）与能力（第 5 章）章节。**只用真实照片，不编造**。
3. **AI 概念图** —— 谨慎，仅纯概念示意（如封面后场景概念图），**不用来冒充真实设备图**（评委看重真实性，AI 设备图与实物不符反减分）。

**配图原则：**
- 图服务于文字，能一图说清的就不堆字（架构、流程、部署、进度优先配图）；
- 每张图配图注（图下方"图 X-X 名称"），正文引用"如图 X-X 所示"；
- 风格统一（配色、字体、线框），由 make_figures.py 保证；
- 图里的技术内容必须与正文一致，不出现正文没有的参数/结构。

## 边界

- 不改大纲结构（发现结构问题提示用户回 bid-outline 调整）。
- 不写商务/价格卷内容。
- 素材缺口标 `[待补]` 后继续写其余部分，不因为缺素材而停整章。
